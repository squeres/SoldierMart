# SoldierMart.kz

Маркетплейс для военнослужащих ВС РК: еда и предметы первой необходимости.
Приложение рассчитано на **терминалы самообслуживания** в части, поэтому телефон солдату не нужен.

Состоит из двух частей:

- **Flutter-приложение** (папка `lib/`): экран терминала.
- **Сервер** (папка `backend/`, Node.js): хранит аккаунты, каталог, баланс, избранное, заказы и счётчики блокировок. Тестовый, для локальной разработки.

## Как это работает

1. Вход в три обязательных шага: **ИИН (12 цифр) → ПИН-код → проверка лица** по камере терминала. Лицо распознаёт сервер: нейросеть превращает снимок в числовой шаблон и сравнивает его с эталоном этого ИИН. Сам снимок не сохраняется. Вводить можно и на экране, и с физической клавиатуры (цифры, `Tab` — другое поле, `Enter` — войти, `Backspace` — стереть символ, `Delete` или `Esc` — стереть поле). Если на экране входа долго никого нет (по умолчанию минута), появляется **заставка-плакат**; введённые цифры при этом стираются. Любое касание или клавиша закрывает её. Время задаётся при сборке: `--dart-define=SAVER_SECONDS=120`, картинка лежит в `assets/images/screensaver.jpg`. Контрольная цифра ИИН проверяется ещё на терминале, ПИН и лицо проверяет сервер. Без проверки лица каталог не открывается. Если камеры нет или доступ запрещён, войти нельзя.
   **Блокировка:**
   - 5 неверных ПИН подряд блокируют аккаунт **временно**: на 15 минут, каждая следующая подряд вдвое дольше, максимум сутки. Так нельзя навсегда заблокировать чужой аккаунт, зная только ИИН. Блокировка снимается сама, дежурный может снять раньше.
   - 3 неудачных проверки лица (при верном ПИН, то есть возможна кража аккаунта) блокируют **жёстко**: снимает только дежурный.
   - Счётчики привязаны к ИИН и хранятся на сервере: перезапуск терминала их не сбрасывает, перебор на другом терминале не помогает. Неизвестный ИИН обрабатывается так же, как известный.
2. Товары: еда, гигиена, одежда, прочее. Поиск, фильтр по категориям, **избранное** (сердечко), привязано к ИИН и хранится на сервере.
3. Заказ: сервер сам считает цену по своему каталогу, проверяет остаток и баланс, списывает деньги и выдаёт **6-значный код выдачи**. Повторная отправка того же заказа (обрыв связи) деньги дважды не спишет. Заказ подтверждается только после записи на диск. Дежурный по коду выдаёт заказ (`ready` → `picked_up`) или отменяет его (деньги и остатки возвращаются). Каждое движение денег пишется в журнал операций.
4. **Помощник** (значок «Помощник» в шапке каталога): чат на русском и казахском. Ищет товары («хочу попить», «есть мыло»), подбирает набор на сумму («что купить на 3000», в пределах баланса) и кладёт его в корзину по кнопке, показывает баланс, коды и статусы заказов, объясняет, как оформить и получить заказ. Помощник только советует, заказ оформляет сам человек. Работает **бесплатно и без нейросети** (по правилам), поэтому всегда отвечает одинаково и не выдумывает товары.
5. **История заказов** (значок чека в шапке каталога): все заказы вошедшего человека с составом, суммой и статусом (ждёт выдачи, выдан, отменён). Пока заказ ждёт выдачи, виден его код. Сервер отдаёт только заказы владельца сеанса, по ИИН из токена, а не из запроса.
6. Через 90 секунд без касаний сеанс завершается автоматически.

## Запуск

### 1. Сервер

Нужен [Node.js](https://nodejs.org) версии 18 или новее.

```bash
cd backend
npm install           # один раз: ставит нейросеть для лиц (около 300 МБ, нужен интернет)
node server.js        # или: npm start
```

При старте сервер печатает адрес (по умолчанию `http://localhost:8080`) и путь к файлу с **админ-ключом** (сам ключ в консоль не выводится). Данные хранятся в **PostgreSQL** (см. раздел «База данных» ниже). Без настройки сервер использует встроенный PostgreSQL в папке `backend/data/pgdata` (удобно для разработки и одного сервера), рядом лежит ключ шифрования `data.key`. Шаблоны лиц в базе зашифрованы (AES-256-GCM).

#### Регистрация лиц (обязательно перед первым входом)

Пока у человека нет эталона лица, войти он не сможет (экран покажет ошибку проверки лица, попытки при этом не сгорают). Эталон записывает дежурный:

1. Откройте в браузере `http://localhost:8080/enroll`.
2. Введите ключ дежурного (файл `backend/data/admin.key`) и ИИН.
3. Человек смотрит в камеру, нажмите «Сделать снимок и сохранить». Лучше 2–3 снимка с небольшими поворотами головы (хранится до 3).

Или из файлов: `npm run enroll -- 030515501234 фото1.jpg фото2.jpg` (первое фото заменяет старый эталон).

Требования к снимку: один человек в кадре, лицо крупное (не меньше 18% ширины кадра), ровный свет. Порог узнавания `0.45` (чем меньше, тем строже), меняется переменной `FACE_THRESHOLD`.

Настройки (переменные окружения):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `PORT` | `8080` | порт |
| `HOST` | `127.0.0.1` | `0.0.0.0` открывает сервер для других устройств в сети |
| `DATA_DIR` | `backend/data` | где хранить данные |
| `ADMIN_KEY` | генерируется в `data/admin.key` | ключ для админ-запросов |
| `DATABASE_URL` | не задан | строка подключения к PostgreSQL, например `postgres://user:pass@host:5432/soldiermart`. Без неё: встроенная база в `DATA_DIR/pgdata` |
| `SEED_DEMO_USERS` | `1` для встроенной базы, иначе не задан | `1` добавляет демо-пользователей с известными ПИН в пустую базу. С `DATABASE_URL` по умолчанию не добавляются |
| `DATA_KEY` | генерируется в `data/data.key` | ключ шифрования шаблонов лиц. В бою держите отдельно от базы. Потеряете ключ, потеряете шаблоны |
| `TLS_CERT`, `TLS_KEY` | не заданы | пути к сертификату и ключу: включают HTTPS |
| `CORS_ORIGINS` | не задан (разрешены все) | разрешённые адреса через запятую, например `https://kiosk.unit.kz` |
| `TRUST_PROXY` | не задан | `1`: сервер за вашим прокси, лимит запросов считается по `X-Forwarded-For` (адрес, дописанный прокси) |
| `RATE_LIMIT_PER_MIN` | `60` | попыток входа в минуту с одного адреса. Если терминалы части выходят через общий NAT, увеличьте |
| `OLLAMA_MODEL`, `OLLAMA_URL` | не заданы | локальная модель для помощника (необязательно) |
| `FACE_MODE` | не задан | `demo` отключает настоящее распознавание: любое лицо проходит, защиты нет |
| `FACE_THRESHOLD` | `0.45` | порог узнавания |
| `FACE_DEMO_RESULT` | не задан | только с `FACE_MODE=demo`: принудительный результат `noMatch`, `noFace`, `error`, `match` |

Windows PowerShell: `$env:FACE_MODE="demo"; node server.js`

Тесты сервера: `cd backend && npm test` (около 20 секунд: в них запускается нейросеть).

#### Помощник

По умолчанию помощник работает по правилам: не нужны ни интернет, ни ключи, ни видеокарта. Запросы разбираются на сервере (`backend/src/assistant/`): слова приводятся к корням, ищутся в каталоге (названия на двух языках и бытовые синонимы: «попить» → вода, чай, кофе), сумма берётся из фразы («3000», «2 500», «3к»). Он видит только каталог в наличии, имя, баланс и последние заказы человека, который вошёл; ИИН, ПИН и биометрия ему недоступны. Лимит: 20 сообщений в минуту на сеанс.

Необязательно можно подключить локальную модель через [Ollama](https://ollama.com) (бесплатно, данные остаются у вас). Она отвечает только на вопросы, которые правила не поняли, и ничего не может оформить или изменить:

```bash
ollama pull qwen2.5:1.5b
OLLAMA_MODEL=qwen2.5:1.5b npm start       # адрес: OLLAMA_URL, по умолчанию http://127.0.0.1:11434
```

Модель умеет составлять списки так же, как правила: на просьбу «подбери», «посоветуй», «покажи списком» она называет коды товаров, а **карточки, настоящие цены, итоговую сумму и кнопку «Добавить всё в корзину» строит сервер**. Выдуманные коды, товары не в наличии и повторы отбрасываются, количество не больше 3 и остатка, а сумма урезается до баланса или названной суммы (маленькие модели плохо считают, деньги проверяет сервер). Если модель назвала товары только словами, сервер находит их в каталоге по названиям, а оборванный ответ не показывается человеку в виде сырого текста. Когда сумма названа («на 2000 покушать») или запрос понятен правилам («что-нибудь тёплое»), отвечают правила, модель не вызывается: они точнее.

Если модель не запущена или не отвечает, помощник отвечает по правилам. Маленькие модели слабо знают казахский и могут ошибаться; одновременно обрабатываются не больше двух вопросов к модели.

#### База данных

Схема создаётся и обновляется сама при старте (таблица `schema_version`, миграции в `backend/src/schema.js`). Несколько серверов могут работать с одной базой: сеансы, шаги входа, счётчики блокировок, заказы и остатки лежат в базе, а не в памяти сервера.

Что гарантирует база:
- деньги и остатки не уходят в минус (ограничения `CHECK`), заказ, списание, остатки и журнал денег проходят одной транзакцией;
- заказ блокирует строки человека и товаров (`FOR UPDATE`), два одновременных заказа не продадут больше остатка;
- повтор запроса с тем же `requestId` не создаёт второй заказ (уникальный индекс);
- счётчики неверных ПИН и лица растут атомарным запросом, блокировка не обходится параллельными попытками, в том числе на разных серверах;
- токены сеансов хранятся только в виде хэша SHA-256.

Встроенная база (без `DATABASE_URL`) нужна только для разработки. Она **не переносит принудительную остановку**: если процесс убить (`Stop-Process -Force`, закрытие окна крестиком, выключение питания), папка `backend/data/pgdata` может остаться повреждённой, и сервер при запуске напишет «Встроенная база не открылась». Останавливайте сервер сочетанием `Ctrl+C`. Если база всё же сломалась, выполните `npm run db:reset`: папка будет переименована в `pgdata.broken-…` (не удалена), и создастся чистая база. Для настоящей работы используйте PostgreSQL.

Боевой запуск:

```bash
createdb soldiermart
DATABASE_URL=postgres://user:pass@localhost:5432/soldiermart node server.js
```

Резервные копии и репликация делаются средствами PostgreSQL (`pg_dump`, потоковая репликация). Файлы сервер больше не копирует.

Перенос данных из старого `db.json` (версия до PostgreSQL), сервер остановить:

```bash
cd backend
DATABASE_URL=postgres://... node migrate-json.js            # в пустую базу
DATABASE_URL=postgres://... node migrate-json.js --replace   # стереть и заменить
```

Перенос идёт одной транзакцией: при ошибке в базе не остаётся ничего. Старый файл не удаляется, рядом появляется `db.json.imported`. Нужен тот же `DATA_KEY`, которым шифровался старый файл.

Что ещё считается в памяти каждого сервера: лимит попыток входа с адреса (`RATE_LIMIT_PER_MIN`) и очередь проверок лица. Это не страшно, но при нескольких серверах лимит действует на каждый отдельно; общий лимит ставьте на прокси.

#### Управление товарами

Страница `http://localhost:8080/panel/catalog` (ссылка «Товары» в панели дежурного, тот же ключ). Можно:

- **добавить товар:** название (русское, казахское необязательно), категория, значок, цена, остаток, код (необязательно);
- **изменить** любое поле, в том числе цену и название; прошлые заказы сохраняют прежние цену и название;
- **изменить остаток:** кнопки −1, +1 и «приход» (на любое число, в том числе отрицательное для списания);
- **скрыть или вернуть в продажу:** скрытый товар исчезает из приложения и избранного и не продаётся, но остаётся в базе;
- **удалить насовсем:** из избранного пропадает, история заказов сохраняется. Если товар есть в заказах, ожидающих выдачи, удалить его нельзя, только скрыть;
- искать по названию или коду, фильтровать по категории и состоянию (в продаже, скрыт, мало, нет в наличии), видеть число проданных штук и стоимость остатков.

Категории и значки ограничены списком из `backend/src/catalog-meta.js`. Новые значения нужно добавить и туда, и в приложение (`lib/models/product.dart`, `lib/data/catalog.dart`).

#### Панель дежурного

Откройте `http://localhost:8080/panel` и введите ключ из `backend/data/admin.key`. Ключ хранится только в открытой вкладке. В панели:

- **Заказы:** очередь «ждут выдачи», выдача по 6-значному коду, отмена с возвратом денег, выданные и отменённые.
- **История человека:** поиск по имени или ИИН, все его заказы (в любых статусах, с возможностью выдать) и движение денег. Просмотр чужой истории пишется в журнал сервера (`admin_view_orders`).
- **Блокировки:** кто и почему заблокирован, до какого времени, кнопка «Разблокировать».
- **Баланс:** пополнение и списание с основанием, журнал операций с остатком.
- **Люди и лица:** у кого есть эталон лица; регистрация лиц открывается по ссылке сверху.

Панель работает поверх запросов ниже.

#### Админ-запросы дежурного

Все с заголовком `X-Admin-Key: <ключ>`, тело JSON.

| Запрос | Что делает |
|---|---|
| `GET/POST /admin/products`, `PUT/DELETE /admin/products/:id`, `POST /admin/products/:id/stock` | управление товарами (то же делает страница `/panel/catalog`) |
| `GET /admin/locked` | список заблокированных (у временных есть `until`) |
| `POST /admin/unlock` `{"iin"}` | снять блокировку и обнулить счётчики |
| `GET /admin/orders?status=ready&iin=` | заказы (`ready`, `picked_up`, `cancelled`, `all`), по желанию одного человека; ИИН замаскирован |
| `GET /admin/users?q=` | поиск человека по имени или ИИН |
| `POST /admin/orders/pickup` `{"code"}` или `{"id"}` | выдать заказ (один раз) |
| `POST /admin/orders/cancel` `{"code"}` или `{"id"}` | отменить до выдачи: деньги и остатки возвращаются |
| `POST /admin/balance` `{"iin","amount","note"}` | пополнить (`amount` > 0) или списать (< 0) баланс |
| `GET /admin/ledger?iin=` | журнал движения денег |
| `GET /admin/enrolled`, `POST /admin/enroll`, `POST /admin/unenroll` | эталоны лиц |

```bash
curl -X POST http://localhost:8080/admin/unlock -H "X-Admin-Key: <ключ>" -H "Content-Type: application/json" -d "{\"iin\":\"030515501234\"}"
curl -X POST http://localhost:8080/admin/balance -H "X-Admin-Key: <ключ>" -H "Content-Type: application/json" -d "{\"iin\":\"030515501234\",\"amount\":5000,\"note\":\"выплата\"}"
```

### 2. Приложение

```bash
flutter pub get
flutter run -d chrome         # или эмулятор / телефон
```

Адрес сервера по умолчанию: `http://localhost:8080` (Chrome, компьютер), `http://10.0.2.2:8080` (эмулятор Android). Для телефона или терминала в той же сети запустите сервер с `HOST=0.0.0.0` и укажите адрес компьютера:

```bash
flutter run --dart-define=API_URL=http://192.168.0.10:8080
```

Android по умолчанию запрещает обычный HTTP. Для разработки добавьте в `<application>` в `AndroidManifest.xml` атрибут `android:usesCleartextTraffic="true"`. В бою нужен HTTPS.

Демо-вход (ИИН вымышленные): `030515501234` / `1234` (25 000 ₸) или `980107304562` / `4321` (8 000 ₸).

Тесты приложения: `flutter test`.

### Разработка без камеры

1. Сервер: `cd backend && npm run dev`. Это демо-режим (лицо не проверяется) и тестовый аккаунт с «зарегистрированным» лицом: ИИН `900101300007`, ПИН `1111`, 50 000 ₸. Аккаунт создаётся только этой командой, в обычном `npm start` его нет.
2. Приложение: `flutter run -d chrome --dart-define=DEV_FAKE_CAMERA=true`. Если камеры нет, на шаге лица вместо неё покажется «DEV: виртуальная камера», кнопка сканирования работает.

Защита от обхода: «снимок» виртуальной камеры пустой, настоящий сервер (с распознаванием) его отклонит. В release-сборке флаг не действует. Без флага при отсутствии камеры войти по-прежнему нельзя.

### Камера

- Android: в `AndroidManifest.xml` добавьте `<uses-permission android:name="android.permission.CAMERA"/>`; `minSdkVersion` не ниже 21.
- Chrome: браузер спросит доступ к камере, нажмите «Разрешить».

## Что уже сделано для надёжности и безопасности

- Блокировка по ПИН временная, с нарастанием; по лицу жёсткая.
- Проверка лица: один запрос на один шаг входа, очередь нейросети ограничена (лишние получают 503), поэтому параллельными запросами блокировку не обойти и сервер не завалить.
- Шаблоны лиц шифруются в базе, запись базы атомарная и не блокирует сервер, ежедневные копии.
- Заказы: статусы, выдача, отмена с возвратом, журнал денег, быстрые индексы вместо перебора истории.
- Поддержка HTTPS, список разрешённых источников CORS, лимит запросов с учётом прокси, админ-ключ не печатается в консоль.
- Точка подключения проверки «живости» (`RealFaceVerifier({ liveness })`, объект с методом `check(image)`).

## Что остаётся сделать перед боевым запуском

- **Проверка «живости» не реализована, есть только точка подключения.** Фотография человека (в том числе на экране телефона), поднесённая к камере, может пройти. Нужна модель защиты от подделки (anti-spoofing) или камера с ИК/глубиной. Качество узнавания зависит от света и камеры: проверьте на реальных терминалах и подберите `FACE_THRESHOLD` на своих людях (для сходных лиц, например братьев, ошибки возможны).
- Используется открытая модель face-api (128-мерный шаблон). Для большой базы людей и жёстких требований безопасности стоит рассмотреть промышленное решение с проверкой на ложные срабатывания.
- **Ключ шифрования `data.key` по умолчанию лежит рядом с базой**: это защищает от копирования одной базы, но не от кражи всей папки. В бою задавайте `DATA_KEY` из хранилища секретов. Биометрия и ИИН — персональные данные. По закону РК они хранятся на серверах в Казахстане, нужны согласие и шифрование. Для военных, вероятно, ещё и закрытая сеть. Согласуйте с юристом и службой безопасности части.
- **PostgreSQL проверен только через встроенную версию (PGlite).** Тесты идут на настоящем движке PostgreSQL, но в одном процессе: реальную конкурентную работу нескольких серверов и драйвер `pg` на отдельном сервере PostgreSQL вам нужно проверить на стенде (нагрузочный тест заказов, отключение сети, переключение на реплику). Резервные копии и репликацию настраивайте и проверяйте восстановлением.
- Включите HTTPS (`TLS_CERT`, `TLS_KEY`) или поставьте сервер за прокси с TLS и задайте `CORS_ORIGINS`. Без TLS токены и админ-ключ идут по сети открытым текстом.
- Админ-запросы защищены одним общим ключом. Для боя нужна отдельная админ-панель с учётными записями дежурных и журналом, кто что делал.
- Для жёсткого киоска настройте на Android lock task mode.
- `backend/data/` содержит данные и ключи: не коммитьте в репозиторий (уже в `.gitignore`). Тестовые фото в `backend/test/faces` проверьте: если это реальные люди, это тоже персональные данные.
